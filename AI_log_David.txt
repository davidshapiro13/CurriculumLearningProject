Prompt:

I'm trying to learn how to use https://gymnasium.farama.org/environments/mujoco/humanoid/ - basically, I want to be able to modify the body and then move the joints and export a video of it. How do I go about doing this?

Response:

You can do this without training an RL agent. **Start by editing the humanoid’s model, setting joint angles directly, and rendering those poses to video.** Once that works, move on to controlling it through physics.

Gymnasium supplies the RL environment; MuJoCo handles the body, joints, physics, and rendering.

**1. Install the packages**

In your project’s virtual environment:

```bash
pip install "gymnasium[mujoco]" imageio imageio-ffmpeg
```

**2. Make an editable copy of the body**

The humanoid is defined in an XML file using MuJoCo’s MJCF format. Copy the installed model into your project:

```python
from pathlib import Path
import shutil
import gymnasium

source = (
    Path(gymnasium.__file__).parent
    / "envs/mujoco/assets/humanoid.xml"
)
shutil.copyfile(source, "my_humanoid.xml")
```

These are the main XML elements you’ll edit:

| Element | What it controls |
|---|---|
| `<body>` | Body hierarchy and attachment locations |
| `<geom>` | Shape, size, appearance, and collision geometry |
| `<joint>` | Rotation axis, movement limits, and damping |
| `<actuator>` | Motors that apply forces to joints |

For a simple first modification, find the head geometry and increase its `size`. When changing limb length, adjust both the limb geometry and the attachment position of its child body so the joints stay connected. The stock model infers inertia from geometry, so size changes also affect its dynamics. [MJCF reference](https://mujoco.readthedocs.io/en/stable/XMLreference.html), [Humanoid model](https://raw.githubusercontent.com/Farama-Foundation/Gymnasium/main/gymnasium/envs/mujoco/assets/humanoid.xml)

**3. Move a joint and export an MP4**

There are two different ways to move joints:

- **Pose animation:** Set joint angles directly. Useful for inspecting your modified body and creating animations.
- **Physics control:** Apply motor commands and advance the simulation. Gravity, momentum, and contacts determine the resulting motion.

Start with pose animation. Save this as `animate_humanoid.py`:

```python
from pathlib import Path

import imageio.v2 as imageio
import mujoco
import numpy as np

model = mujoco.MjModel.from_xml_path(
    str(Path("my_humanoid.xml").resolve())
)
data = mujoco.MjData(model)

# Print available joints so you can choose others to animate.
for i in range(model.njnt):
    print(i, model.joint(i).name)

# A joint's ID and its position in qpos are not necessarily the same.
joint = model.joint("right_elbow")
qpos_index = int(joint.qposadr[0])

# Compiled hinge-joint limits and qpos angles are in radians.
lower, upper = joint.range
midpoint = (lower + upper) / 2
amplitude = 0.4 * (upper - lower)

initial_pose = data.qpos.copy()

camera = mujoco.MjvCamera()
camera.lookat[:] = [0, 0, 1.2]
camera.distance = 4
camera.azimuth = 135
camera.elevation = -15

fps = 30
duration = 5

with mujoco.Renderer(model, height=480, width=640) as renderer:
    with imageio.get_writer(
        "humanoid.mp4", fps=fps, codec="libx264"
    ) as video:
        for frame in range(fps * duration):
            t = frame / fps

            data.qpos[:] = initial_pose
            data.qpos[qpos_index] = (
                midpoint + amplitude * np.sin(2 * np.pi * 0.5 * t)
            )
            data.qvel[:] = 0

            # Update body positions from the pose, without advancing time.
            mujoco.mj_forward(model, data)

            renderer.update_scene(data, camera=camera)
            video.append_data(renderer.render())

print("Saved humanoid.mp4")
```

Run:

```bash
python animate_humanoid.py
```

This produces a five-second video of the elbow moving while the rest of the body stays posed. Because it doesn’t call `mj_step`, gravity won’t make the humanoid fall. Direct state access and forward computation are provided by the [MuJoCo Python API](https://mujoco.readthedocs.io/en/stable/python.html).

**4. Introduce physics when you’re ready**

You can load the edited XML into Gymnasium:

```python
from pathlib import Path
import gymnasium as gym

env = gym.make(
    "Humanoid-v5",
    xml_file=str(Path("my_humanoid.xml").resolve()),
    render_mode="rgb_array",
)

observation, info = env.reset(seed=0)

action = env.action_space.sample()
observation, reward, terminated, truncated, info = env.step(action)
frame = env.render()

env.close()
```

The stock humanoid has **17 motor-control inputs**. These apply forces through its actuators; they are **not desired joint angles**. Random actions will usually make it fall. To reach target angles under physics, you need a controller—such as PD control—or position actuators; standing and walking additionally require balance control. Gymnasium supports custom model paths through `xml_file`. [Humanoid documentation](https://gymnasium.farama.org/environments/mujoco/humanoid/)

For your immediate goal, the XML-editing → pose-animation → MP4 workflow gives you a useful starting point before introducing the difficulty of balance.

Prompt:

Explain the animate_humanoid code

Response:

Your script creates a **five-second video of the humanoid bending its right elbow**. Each frame follows this sequence:

**Set the pose → update body positions → render an image → append it to the video.**

It sets angles directly, so there’s no controller or RL agent involved.

**1. Load the body and create its state**

```python
model = mujoco.MjModel.from_xml_path(
    str(Path("my_humanoid.xml").resolve())
)
data = mujoco.MjData(model)
```

MuJoCo separates two things:

- **`model`**: The body’s definition—limb shapes, joints, masses, movement limits, etc.
- **`data`**: Its current state—joint positions, velocities, and other changing quantities.

`Path(...).resolve()` converts the XML filename into an absolute path. It looks relative to **the directory where you run the command**, which may differ from the script’s directory.

**2. Find the elbow’s angle in the state**

```python
for i in range(model.njnt):
    print(i, model.joint(i).name)
```

This prints every joint’s ID and name so you can discover which joints are available.

```python
joint = model.joint("right_elbow")
qpos_index = int(joint.qposadr[0])
```

`data.qpos` is the array containing the humanoid’s position coordinates, including joint angles.

`qposadr` tells you where this particular joint’s coordinate starts in that array. **A joint ID is not necessarily its array index:** a hinge needs one angle, while a free joint uses multiple coordinates for position and orientation.

For this elbow hinge:

```python
data.qpos[qpos_index]
```

is its angle in radians.

**3. Choose how far the elbow moves**

```python
lower, upper = joint.range
midpoint = (lower + upper) / 2
amplitude = 0.4 * (upper - lower)
```

These calculate a motion centered within the elbow’s allowed range.

For example, if the range were `0–100°`:

| Quantity | Value |
|---|---:|
| Midpoint | 50° |
| Amplitude | 40° |
| Animated range | 10–90° |

Using `0.4` leaves some space before either limit. These calculations actually use radians; degrees here are just for illustration.

```python
initial_pose = data.qpos.copy()
```

This saves the starting pose. `.copy()` creates a separate array so later changes to `data.qpos` won’t change the saved pose.

**4. Set up the camera**

```python
camera = mujoco.MjvCamera()
camera.lookat[:] = [0, 0, 1.2]
camera.distance = 4
camera.azimuth = 135
camera.elevation = -15
```

These settings mean:

- Look toward the point `(0, 0, 1.2)`.
- Place the camera 4 distance units from that point.
- Rotate around the subject by an azimuth of 135°.
- Use an elevation of −15°, giving a downward viewing angle.

The `[:]` syntax updates the contents of an existing array.

**5. Create the renderer and video writer**

```python
fps = 30
duration = 5
```

That gives **150 frames**.

```python
with mujoco.Renderer(model, height=480, width=640) as renderer:
    with imageio.get_writer(
        "humanoid.mp4", fps=fps, codec="libx264"
    ) as video:
```

The renderer creates 640 × 480 images. The video writer encodes those images into an H.264 MP4.

The `with` blocks automatically close the renderer and finish writing the video when the blocks end.

**6. Calculate the pose for each frame**

```python
for frame in range(fps * duration):
    t = frame / fps
```

`t` is the time represented by the frame: `0`, `1/30`, `2/30` seconds, and so on. The script doesn’t need to run in real time; the video’s playback rate controls timing.

```python
data.qpos[:] = initial_pose
```

Restore the starting pose so every joint begins each frame at its original position.

```python
data.qpos[qpos_index] = (
    midpoint + amplitude * np.sin(2 * np.pi * 0.5 * t)
)
```

This moves the elbow smoothly back and forth:

```text
angle = center + movement_size × sin(2π × frequency × time)
```

The frequency is `0.5` cycles per second, so one full bend-and-return cycle takes **two seconds**. Change `0.5` to `1.0` to double the speed.

```python
data.qvel[:] = 0
```

This sets all joint velocities to zero. The animation comes from explicitly changing positions each frame.

**7. Update geometry and save the frame**

```python
mujoco.mj_forward(model, data)
```

After changing the joint angle, MuJoCo needs to recompute the resulting body positions and other derived quantities. For example, bending the elbow changes where the forearm and hand are.

**`mj_forward` does not advance simulation time.** Because this script never calls `mj_step`, gravity doesn’t make the body fall, and physics doesn’t determine its movement.

```python
renderer.update_scene(data, camera=camera)
video.append_data(renderer.render())
```

The first line updates the scene using the current pose and camera. The second renders an image and adds it to the MP4.

To experiment, change `"right_elbow"` to another **hinge joint name** from the printed list, adjust `0.4` for movement size, or adjust `0.5` for speed.

Prompt:

Ok, say I wanted to have the humanoid kick their leg

Response:

For a kick, coordinate **two joints**: raise the thigh at the hip, then straighten the knee.

In your model:

- `right_hip_y`: negative angles lift the leg forward.
- `right_knee`: negative angles bend the knee; approaching −2° straightens it.

A simple kick can use a sequence of **keyframes**, which are poses at specific times:

| Time | Hip | Knee | Pose |
|---|---:|---:|---|
| 0.0 s | 0° | −2° | Standing |
| 0.6 s | −60° | −90° | Raise thigh, bend knee |
| 0.9 s | −70° | −5° | Extend the kick |
| 1.3 s | −60° | −90° | Retract |
| 2.0 s | 0° | −2° | Lower leg |

Replace your elbow-selection and amplitude code with:

```python
hip_index = int(model.joint("right_hip_y").qposadr[0])
knee_index = int(model.joint("right_knee").qposadr[0])

key_times = np.array([0.0, 0.6, 0.9, 1.3, 2.0])

# Write readable angles in degrees, then convert to radians.
hip_angles = np.deg2rad([0, -60, -70, -60, 0])
knee_angles = np.deg2rad([-2, -90, -5, -90, -2])

initial_pose = data.qpos.copy()
```

Then replace the pose-setting portion inside your frame loop with:

```python
t = frame / fps
kick_time = t % 2.5  # Repeat every 2.5 seconds, including a pause.

data.qpos[:] = initial_pose

data.qpos[hip_index] = np.interp(
    kick_time, key_times, hip_angles
)
data.qpos[knee_index] = np.interp(
    kick_time, key_times, knee_angles
)

data.qvel[:] = 0

mujoco.mj_forward(model, data)
renderer.update_scene(data, camera=camera)
video.append_data(renderer.render())
```

**`np.interp` fills in the angles between keyframes.** For example, halfway between the standing pose and the raised-leg pose, the hip is at −30° and the knee at −46°. After the final keyframe, it holds the standing pose until the next cycle.

Keep the camera and video-writing code unchanged. This creates a posed kick animation; making the humanoid physically balance and kick would require motor control and simulation steps.

Prompt:

Ok, so our RL will outpul the degrees to move the humanoid. But how can I modify the humanoid to have the specific joints we want?

Response:

You define the humanoid’s joints in **`my_humanoid.xml`**. The XML describes the body parts, how they connect, and which movements each connection allows.

One important distinction first: **your RL policy can output target joint angles, but the default Gymnasium Humanoid expects motor commands, not angles.** You’ll need position actuators or a controller that converts your target angles into motor forces.

**How joints are defined**

A `<body>` represents a rigid body part. A `<joint>` inside it allows that body to move relative to its parent.

For example:

```xml
<body name="thigh" pos="0 0 -0.2">
    <joint
        name="hip"
        type="hinge"
        axis="0 1 0"
        range="-110 20"
    />

    <geom
        type="capsule"
        fromto="0 0 0  0 0 -0.4"
        size="0.05"
    />

    <body name="shin" pos="0 0 -0.4">
        <joint
            name="knee"
            type="hinge"
            axis="0 1 0"
            range="0 150"
        />

        <geom
            type="capsule"
            fromto="0 0 0  0 0 -0.4"
            size="0.04"
        />
    </body>
</body>
```

Here, moving the hip moves **both the thigh and shin**. Moving the knee moves the shin relative to the thigh.

The main joint properties are:

| Property | Meaning |
|---|---|
| `name` | Identifier used in Python and actuator definitions |
| `type="hinge"` | Rotation around one axis |
| `axis` | Rotation axis in the body’s local coordinates |
| `pos` | Joint location in the body’s local coordinates |
| `range` | Allowed movement |
| `damping` | Resistance to joint velocity |

Your XML uses degrees for angle definitions, but **MuJoCo’s runtime joint angles use radians**.

**Choosing which movements to allow**

For a hip with forward/backward and sideways motion, define two hinges on the thigh:

```xml
<joint name="hip_forward" type="hinge"
       axis="0 1 0" range="-110 20"/>

<joint name="hip_sideways" type="hinge"
       axis="1 0 0" range="-30 30"/>
```

That gives the hip **two degrees of freedom**. Add a third hinge around the remaining axis if you also want twisting.

For your existing humanoid:

- Edit an existing joint’s `range` to change its permitted motion.
- Remove a joint to eliminate that degree of freedom.
- Add a hinge to an existing body to allow another rotation.
- Add a child `<body>` with a joint to introduce a new articulated part, such as a movable foot.

When removing or renaming a joint, also update any **actuators and tendons that reference it**. Your current model has both.

**Making the policy output target angles**

A position actuator can drive a joint toward a requested angle. For example, replacing the knee’s existing motor with:

```xml
<position
    name="knee_target"
    joint="right_knee"
    kp="100"
    ctrllimited="true"
    ctrlrange="-2.79 -0.035"
/>
```

would make its control input a target angle in radians, approximately −160° to −2°. The gain `kp` determines how strongly it pushes toward that target; it needs tuning, along with damping and force limits, for your body.

The resulting workflow is:

```text
RL action
   ↓
Map action to allowed target angles
   ↓
Position actuators apply forces
   ↓
MuJoCo simulates the resulting movement
   ↓
Observation and reward
```

Unlike the animation script, you would **not overwrite `qpos` every step**. The policy supplies targets, and physics determines whether—and how—the joints reach them.

After changing the joint structure, reload the XML and adapt your policy’s action dimensions and observation handling. Large body changes may also require adjusting Humanoid’s reward and standing-height criteria.

**Which joints and movements do you want—for example, hips with two rotations, knees with one, and ankles with two?** That list determines the XML structure and the number of outputs your policy needs.

Prompt:

you meantioned something about physics

Response:

Yes—there’s an important difference between **the videos we’re making now** and **what happens during RL training**.

Currently, the animation sets joint angles directly:

```python
data.qpos[index] = angle
mujoco.mj_forward(model, data)
```

This tells MuJoCo, “Put the joint here.” It updates the body’s pose without advancing time. Gravity doesn’t make it fall, and collisions don’t stop us from placing limbs inside one another.

With physics, we instead give the actuators **target angles** and advance the simulation:

```python
data.ctrl[:] = np.deg2rad(target_angles_degrees)
mujoco.mj_step(model, data)
```

Our position actuators apply forces to move toward those targets. The resulting motion depends on:

- **Mass and inertia:** Limbs take time and effort to accelerate.
- **Gravity:** The humanoid can fall.
- **Contact and friction:** Feet push against the floor and can slip.
- **Actuator strength:** Motors may not reach the requested angles under load.

For example, requesting a 70° hip bend instantly places the thigh there in our animation. Under physics, the motor gradually raises it—and the humanoid might lose balance while doing so.

For your RL project, the loop will be:

**Policy chooses 20 target angles → motors apply forces → physics advances → policy receives the new state and reward.**

When using Gymnasium, `env.step(action)` handles the physics steps for you. The model is already configured for target-angle control, but the current videos only demonstrate its range of movement; they don’t establish that it can physically stand or kick.
