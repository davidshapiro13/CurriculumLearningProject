Prompt:

I'm trying to learn how to use https://gymnasium.farama.org/environments/mujoco/humanoid/ - basically, I want to be able to modify the body and then move the joints and export a video of it. How do I go about doing this?

Response:

You can do this without training an RL agent. **Start by editing the humanoid’s model, setting joint angles directly, and rendering those poses to video.** Once that works, move on to controlling it through physics.

Gymnasium supplies the RL environment; MuJoCo handles the body, joints, physics, and rendering.

**1. Install the packages**

In your project’s virtual environment:

```bash
pip install "gymnasium[mujoco]" imageio imageio-ffmpeg
```

**2. Make an editable copy of the body**

The humanoid is defined in an XML file using MuJoCo’s MJCF format. Copy the installed model into your project:

```python
from pathlib import Path
import shutil
import gymnasium

source = (
    Path(gymnasium.__file__).parent
    / "envs/mujoco/assets/humanoid.xml"
)
shutil.copyfile(source, "my_humanoid.xml")
```

These are the main XML elements you’ll edit:

| Element | What it controls |
|---|---|
| `<body>` | Body hierarchy and attachment locations |
| `<geom>` | Shape, size, appearance, and collision geometry |
| `<joint>` | Rotation axis, movement limits, and damping |
| `<actuator>` | Motors that apply forces to joints |

For a simple first modification, find the head geometry and increase its `size`. When changing limb length, adjust both the limb geometry and the attachment position of its child body so the joints stay connected. The stock model infers inertia from geometry, so size changes also affect its dynamics. [MJCF reference](https://mujoco.readthedocs.io/en/stable/XMLreference.html), [Humanoid model](https://raw.githubusercontent.com/Farama-Foundation/Gymnasium/main/gymnasium/envs/mujoco/assets/humanoid.xml)

**3. Move a joint and export an MP4**

There are two different ways to move joints:

- **Pose animation:** Set joint angles directly. Useful for inspecting your modified body and creating animations.
- **Physics control:** Apply motor commands and advance the simulation. Gravity, momentum, and contacts determine the resulting motion.

Start with pose animation. Save this as `animate_humanoid.py`:

```python
from pathlib import Path

import imageio.v2 as imageio
import mujoco
import numpy as np

model = mujoco.MjModel.from_xml_path(
    str(Path("my_humanoid.xml").resolve())
)
data = mujoco.MjData(model)

# Print available joints so you can choose others to animate.
for i in range(model.njnt):
    print(i, model.joint(i).name)

# A joint's ID and its position in qpos are not necessarily the same.
joint = model.joint("right_elbow")
qpos_index = int(joint.qposadr[0])

# Compiled hinge-joint limits and qpos angles are in radians.
lower, upper = joint.range
midpoint = (lower + upper) / 2
amplitude = 0.4 * (upper - lower)

initial_pose = data.qpos.copy()

camera = mujoco.MjvCamera()
camera.lookat[:] = [0, 0, 1.2]
camera.distance = 4
camera.azimuth = 135
camera.elevation = -15

fps = 30
duration = 5

with mujoco.Renderer(model, height=480, width=640) as renderer:
    with imageio.get_writer(
        "humanoid.mp4", fps=fps, codec="libx264"
    ) as video:
        for frame in range(fps * duration):
            t = frame / fps

            data.qpos[:] = initial_pose
            data.qpos[qpos_index] = (
                midpoint + amplitude * np.sin(2 * np.pi * 0.5 * t)
            )
            data.qvel[:] = 0

            # Update body positions from the pose, without advancing time.
            mujoco.mj_forward(model, data)

            renderer.update_scene(data, camera=camera)
            video.append_data(renderer.render())

print("Saved humanoid.mp4")
```

Run:

```bash
python animate_humanoid.py
```

This produces a five-second video of the elbow moving while the rest of the body stays posed. Because it doesn’t call `mj_step`, gravity won’t make the humanoid fall. Direct state access and forward computation are provided by the [MuJoCo Python API](https://mujoco.readthedocs.io/en/stable/python.html).

**4. Introduce physics when you’re ready**

You can load the edited XML into Gymnasium:

```python
from pathlib import Path
import gymnasium as gym

env = gym.make(
    "Humanoid-v5",
    xml_file=str(Path("my_humanoid.xml").resolve()),
    render_mode="rgb_array",
)

observation, info = env.reset(seed=0)

action = env.action_space.sample()
observation, reward, terminated, truncated, info = env.step(action)
frame = env.render()

env.close()
```

The stock humanoid has **17 motor-control inputs**. These apply forces through its actuators; they are **not desired joint angles**. Random actions will usually make it fall. To reach target angles under physics, you need a controller—such as PD control—or position actuators; standing and walking additionally require balance control. Gymnasium supports custom model paths through `xml_file`. [Humanoid documentation](https://gymnasium.farama.org/environments/mujoco/humanoid/)

For your immediate goal, the XML-editing → pose-animation → MP4 workflow gives you a useful starting point before introducing the difficulty of balance.

Prompt:

Explain the animate_humanoid code

Response:

Your script creates a **five-second video of the humanoid bending its right elbow**. Each frame follows this sequence:

**Set the pose → update body positions → render an image → append it to the video.**

It sets angles directly, so there’s no controller or RL agent involved.

**1. Load the body and create its state**

```python
model = mujoco.MjModel.from_xml_path(
    str(Path("my_humanoid.xml").resolve())
)
data = mujoco.MjData(model)
```

MuJoCo separates two things:

- **`model`**: The body’s definition—limb shapes, joints, masses, movement limits, etc.
- **`data`**: Its current state—joint positions, velocities, and other changing quantities.

`Path(...).resolve()` converts the XML filename into an absolute path. It looks relative to **the directory where you run the command**, which may differ from the script’s directory.

**2. Find the elbow’s angle in the state**

```python
for i in range(model.njnt):
    print(i, model.joint(i).name)
```

This prints every joint’s ID and name so you can discover which joints are available.

```python
joint = model.joint("right_elbow")
qpos_index = int(joint.qposadr[0])
```

`data.qpos` is the array containing the humanoid’s position coordinates, including joint angles.

`qposadr` tells you where this particular joint’s coordinate starts in that array. **A joint ID is not necessarily its array index:** a hinge needs one angle, while a free joint uses multiple coordinates for position and orientation.

For this elbow hinge:

```python
data.qpos[qpos_index]
```

is its angle in radians.

**3. Choose how far the elbow moves**

```python
lower, upper = joint.range
midpoint = (lower + upper) / 2
amplitude = 0.4 * (upper - lower)
```

These calculate a motion centered within the elbow’s allowed range.

For example, if the range were `0–100°`:

| Quantity | Value |
|---|---:|
| Midpoint | 50° |
| Amplitude | 40° |
| Animated range | 10–90° |

Using `0.4` leaves some space before either limit. These calculations actually use radians; degrees here are just for illustration.

```python
initial_pose = data.qpos.copy()
```

This saves the starting pose. `.copy()` creates a separate array so later changes to `data.qpos` won’t change the saved pose.

**4. Set up the camera**

```python
camera = mujoco.MjvCamera()
camera.lookat[:] = [0, 0, 1.2]
camera.distance = 4
camera.azimuth = 135
camera.elevation = -15
```

These settings mean:

- Look toward the point `(0, 0, 1.2)`.
- Place the camera 4 distance units from that point.
- Rotate around the subject by an azimuth of 135°.
- Use an elevation of −15°, giving a downward viewing angle.

The `[:]` syntax updates the contents of an existing array.

**5. Create the renderer and video writer**

```python
fps = 30
duration = 5
```

That gives **150 frames**.

```python
with mujoco.Renderer(model, height=480, width=640) as renderer:
    with imageio.get_writer(
        "humanoid.mp4", fps=fps, codec="libx264"
    ) as video:
```

The renderer creates 640 × 480 images. The video writer encodes those images into an H.264 MP4.

The `with` blocks automatically close the renderer and finish writing the video when the blocks end.

**6. Calculate the pose for each frame**

```python
for frame in range(fps * duration):
    t = frame / fps
```

`t` is the time represented by the frame: `0`, `1/30`, `2/30` seconds, and so on. The script doesn’t need to run in real time; the video’s playback rate controls timing.

```python
data.qpos[:] = initial_pose
```

Restore the starting pose so every joint begins each frame at its original position.

```python
data.qpos[qpos_index] = (
    midpoint + amplitude * np.sin(2 * np.pi * 0.5 * t)
)
```

This moves the elbow smoothly back and forth:

```text
angle = center + movement_size × sin(2π × frequency × time)
```

The frequency is `0.5` cycles per second, so one full bend-and-return cycle takes **two seconds**. Change `0.5` to `1.0` to double the speed.

```python
data.qvel[:] = 0
```

This sets all joint velocities to zero. The animation comes from explicitly changing positions each frame.

**7. Update geometry and save the frame**

```python
mujoco.mj_forward(model, data)
```

After changing the joint angle, MuJoCo needs to recompute the resulting body positions and other derived quantities. For example, bending the elbow changes where the forearm and hand are.

**`mj_forward` does not advance simulation time.** Because this script never calls `mj_step`, gravity doesn’t make the body fall, and physics doesn’t determine its movement.

```python
renderer.update_scene(data, camera=camera)
video.append_data(renderer.render())
```

The first line updates the scene using the current pose and camera. The second renders an image and adds it to the MP4.

To experiment, change `"right_elbow"` to another **hinge joint name** from the printed list, adjust `0.4` for movement size, or adjust `0.5` for speed.

In your model:

A simple kick can use a sequence of **keyframes**, which are poses at specific times:

| Time | Hip | Knee | Pose |
|---|---:|---:|---|
| 0.0 s | 0° | −2° | Standing |
| 0.6 s | −60° | −90° | Raise thigh, bend knee |
| 0.9 s | −70° | −5° | Extend the kick |
| 1.3 s | −60° | −90° | Retract |
| 2.0 s | 0° | −2° | Lower leg |

Replace your elbow-selection and amplitude code with:

```python
hip_index = int(model.joint("right_hip_y").qposadr[0])
knee_index = int(model.joint("right_knee").qposadr[0])

key_times = np.array([0.0, 0.6, 0.9, 1.3, 2.0])

# Write readable angles in degrees, then convert to radians.
hip_angles = np.deg2rad([0, -60, -70, -60, 0])
knee_angles = np.deg2rad([-2, -90, -5, -90, -2])

initial_pose = data.qpos.copy()
```

Then replace the pose-setting portion inside your frame loop with:

```python
t = frame / fps
kick_time = t % 2.5  # Repeat every 2.5 seconds, including a pause.

data.qpos[:] = initial_pose

data.qpos[hip_index] = np.interp(
    kick_time, key_times, hip_angles
)
data.qpos[knee_index] = np.interp(
    kick_time, key_times, knee_angles
)

data.qvel[:] = 0

mujoco.mj_forward(model, data)
renderer.update_scene(data, camera=camera)
video.append_data(renderer.render())
```

**`np.interp` fills in the angles between keyframes.** For example, halfway between the standing pose and the raised-leg pose, the hip is at −30° and the knee at −46°. After the final keyframe, it holds the standing pose until the next cycle.

Keep the camera and video-writing code unchanged. This creates a posed kick animation; making the humanoid physically balance and kick would require motor control and simulation steps.

Prompt:

Ok, so our RL will outpul the degrees to move the humanoid. But how can I modify the humanoid to have the specific joints we want?

Response:

You define the humanoid’s joints in **`my_humanoid.xml`**. The XML describes the body parts, how they connect, and which movements each connection allows.

One important distinction first: **your RL policy can output target joint angles, but the default Gymnasium Humanoid expects motor commands, not angles.** You’ll need position actuators or a controller that converts your target angles into motor forces.

**How joints are defined**

A `<body>` represents a rigid body part. A `<joint>` inside it allows that body to move relative to its parent.

For example:

```xml
<body name="thigh" pos="0 0 -0.2">
    <joint
        name="hip"
        type="hinge"
        axis="0 1 0"
        range="-110 20"
    />

    <geom
        type="capsule"
        fromto="0 0 0  0 0 -0.4"
        size="0.05"
    />

    <body name="shin" pos="0 0 -0.4">
        <joint
            name="knee"
            type="hinge"
            axis="0 1 0"
            range="0 150"
        />

        <geom
            type="capsule"
            fromto="0 0 0  0 0 -0.4"
            size="0.04"
        />
    </body>
</body>
```

Here, moving the hip moves **both the thigh and shin**. Moving the knee moves the shin relative to the thigh.

The main joint properties are:

| Property | Meaning |
|---|---|
| `name` | Identifier used in Python and actuator definitions |
| `type="hinge"` | Rotation around one axis |
| `axis` | Rotation axis in the body’s local coordinates |
| `pos` | Joint location in the body’s local coordinates |
| `range` | Allowed movement |
| `damping` | Resistance to joint velocity |

Your XML uses degrees for angle definitions, but **MuJoCo’s runtime joint angles use radians**.

**Choosing which movements to allow**

For a hip with forward/backward and sideways motion, define two hinges on the thigh:

```xml
<joint name="hip_forward" type="hinge"
       axis="0 1 0" range="-110 20"/>

<joint name="hip_sideways" type="hinge"
       axis="1 0 0" range="-30 30"/>
```

That gives the hip **two degrees of freedom**. Add a third hinge around the remaining axis if you also want twisting.

For your existing humanoid:

- Edit an existing joint’s `range` to change its permitted motion.
- Remove a joint to eliminate that degree of freedom.
- Add a hinge to an existing body to allow another rotation.
- Add a child `<body>` with a joint to introduce a new articulated part, such as a movable foot.

When removing or renaming a joint, also update any **actuators and tendons that reference it**. Your current model has both.

**Making the policy output target angles**

A position actuator can drive a joint toward a requested angle. For example, replacing the knee’s existing motor with:

```xml
<position
    name="knee_target"
    joint="right_knee"
    kp="100"
    ctrllimited="true"
    ctrlrange="-2.79 -0.035"
/>
```

would make its control input a target angle in radians, approximately −160° to −2°. The gain `kp` determines how strongly it pushes toward that target; it needs tuning, along with damping and force limits, for your body.

The resulting workflow is:

```text
RL action
   ↓
Map action to allowed target angles
   ↓
Position actuators apply forces
   ↓
MuJoCo simulates the resulting movement
   ↓
Observation and reward
```

Unlike the animation script, you would **not overwrite `qpos` every step**. The policy supplies targets, and physics determines whether—and how—the joints reach them.

After changing the joint structure, reload the XML and adapt your policy’s action dimensions and observation handling. Large body changes may also require adjusting Humanoid’s reward and standing-height criteria.

**Which joints and movements do you want—for example, hips with two rotations, knees with one, and ankles with two?** That list determines the XML structure and the number of outputs your policy needs.

Prompt:

you meantioned something about physics

Response:

Yes—there’s an important difference between **the videos we’re making now** and **what happens during RL training**.

Currently, the animation sets joint angles directly:

```python
data.qpos[index] = angle
mujoco.mj_forward(model, data)
```

This tells MuJoCo, “Put the joint here.” It updates the body’s pose without advancing time. Gravity doesn’t make it fall, and collisions don’t stop us from placing limbs inside one another.

With physics, we instead give the actuators **target angles** and advance the simulation:

```python
data.ctrl[:] = np.deg2rad(target_angles_degrees)
mujoco.mj_step(model, data)
```

Our position actuators apply forces to move toward those targets. The resulting motion depends on:

- **Mass and inertia:** Limbs take time and effort to accelerate.
- **Gravity:** The humanoid can fall.
- **Contact and friction:** Feet push against the floor and can slip.
- **Actuator strength:** Motors may not reach the requested angles under load.

For example, requesting a 70° hip bend instantly places the thigh there in our animation. Under physics, the motor gradually raises it—and the humanoid might lose balance while doing so.

For your RL project, the loop will be:

**Policy chooses 20 target angles → motors apply forces → physics advances → policy receives the new state and reward.**

When using Gymnasium, `env.step(action)` handles the physics steps for you. The model is already configured for target-angle control, but the current videos only demonstrate its range of movement; they don’t establish that it can physically stand or kick.

Prompt:

how will i know how much longer it will take?

Response:

PPO prints progress tables while training. Look for:

- **`total_timesteps`**: training steps completed.
- **`fps`**: training steps processed per second.
- **`time_elapsed`**: elapsed seconds.

Estimate the remaining time with:

```text
remaining seconds = (requested timesteps − total_timesteps) / fps
```

For example, with 1,000,000 requested steps, 200,000 completed, and 2,000 fps:

```text
800,000 / 2,000 = 400 seconds ≈ 6 minutes 40 seconds
```

Use the speed shown after a few progress updates; the initial estimate can fluctuate.

**That estimates when the training run finishes—not when the humanoid learns to walk.** Watch `ep_len_mean`: approaching 1,000 means it survives longer, but you’ll still need to inspect the evaluation video to see whether it walks.

Prompt:

Tell me how this was implemented so I have an understanding of the learning method, paramters, rewards ,etc

Response:

The current implementation uses **PPO to learn motor commands through trial and error in MuJoCo**. We wrote the environment, reward, episode rules, and training setup in `LearningMujoco/train_walking.py`; Stable-Baselines3 supplies the PPO algorithm.

This explanation describes the **current original 17-motor model**, not the earlier 20-joint version.

**1. What happens during training**

The loop is:

```text
Read the humanoid’s state
          ↓
Policy chooses 17 motor commands
          ↓
MuJoCo simulates the resulting motion
          ↓
Calculate reward and check for a fall
          ↓
Store the experience
          ↓
After 512 steps, update the neural networks
```

There are no walking demonstrations or predefined leg movements. The policy starts with randomly initialized weights and learns which actions produce higher rewards. **There is currently no curriculum learning**—every episode starts with the full, unsupported humanoid under gravity.

**2. What the policy observes**

Each observation contains **348 numbers**:

| Information | Count |
|---|---:|
| Root height, orientation, and joint angles | 22 |
| Root and joint velocities | 23 |
| Body inertia information | 130 |
| Body linear/angular velocities | 78 |
| Actuator forces on controlled joints | 17 |
| External forces and torques on bodies | 78 |
| **Total** | **348** |

Absolute horizontal position is excluded. This helps the policy choose actions based on its physical state rather than a particular location on the floor.

The policy receives simulator measurements, **not camera images**.

**3. What it controls**

The policy produces **17 motor commands**, each clipped to `[-0.4, 0.4]`.

These control:

- Three abdomen rotations.
- Three hip rotations per leg.
- One knee rotation per leg.
- Two shoulder rotations per arm.
- One elbow rotation per arm.

These are **not target angles**. The XML’s motor gearing converts each command into joint torque. The resulting angle depends on that torque, gravity, inertia, contacts, and other forces.

During training, actions are sampled from a Gaussian distribution to provide exploration. During evaluation, we use the policy’s mean action without that exploration noise.

**4. Simulation timing and episodes**

| Setting | Value |
|---|---:|
| Physics timestep | 0.003 seconds |
| Physics steps per policy action | 5 |
| Normal duration of one action | 0.015 seconds |
| Policy decisions per simulated second | About 66.7 |
| Maximum episode length | 1,000 policy steps |
| Maximum simulated episode duration | About 15 seconds |

An episode ends when:

- **Fall:** any body other than the feet touches the floor.
- **Timeout:** it reaches 1,000 policy steps.

We check contacts after **every physics substep**, so a brief impact between policy decisions still counts. Positive-distance proximity contacts do not count as touching.

A fall is reported as `terminated=True`; a timeout is `truncated=True`. That distinction matters because PPO can treat a time limit as an artificial interruption rather than a failed terminal state.

At reset, we restore the starting pose and add small random perturbations to positions and velocities, uniformly between `−0.01` and `0.01` in their respective coordinate units.

**5. The reward**

The current reward per policy step is:

\[
r = 1.25v_x + r_{\text{upright}}
    - 0.1\sum_i a_i^2
    - \min\left(5\times10^{-7}\sum_j F_j^2,\ 10\right)
\]

Here is what each term means:

| Term | Purpose |
|---|---|
| `1.25 × forward_velocity` | Reward moving the whole-body center of mass in world `+X` |
| Upright reward | Give `+5` when root height is between 1 and 2 meters and no fall occurred |
| Control cost | Penalize large motor commands |
| Contact cost | Penalize large external contact forces/torques, capped at 10 |

For example, moving forward at 1 m/s while receiving the upright reward gives **6.25 reward before costs**.

There are several important details:

- The “upright” condition checks **height**, not torso orientation directly.
- There is **no separate fixed fall penalty** in the current implementation. A fall ends the episode and removes future reward.
- There is no explicit reward for alternating feet, a particular gait, smooth movement, or maintaining a target walking speed.
- The control cost is a penalty on squared commands, not a measurement of mechanical energy.

The reward therefore specifies **forward movement and survival**, but does not fully specify what we would visually recognize as good walking.

**6. How PPO learns**

PPO uses two neural networks:

| Network | Job | Architecture |
|---|---|---|
| Actor/policy | Choose motor commands | 348 inputs → 256 → 256 → 17 action means |
| Critic/value | Predict future discounted reward | 348 inputs → 256 → 256 → 1 value |

Both use ReLU activations. The actor also learns the action distribution’s standard deviations.

For each training update:

1. Collect 512 steps using the current policy. This can span several episodes.
2. Estimate which actions performed better or worse than the critic expected. This estimate is called the **advantage**.
3. Make advantageous actions more likely and disadvantageous actions less likely.
4. Update the critic to better predict returns.

PPO’s clipped objective discourages excessively large policy changes during an update. It is not a hard guarantee that behavior will only change a little. [Stable-Baselines3 PPO documentation](https://stable-baselines3.readthedocs.io/en/master/modules/ppo.html)

**7. The training parameters**

These are the values explicitly configured in the current script:

| Parameter | Value | Meaning |
|---|---:|---|
| `learning_rate` | `0.0000356987` | Size of optimizer updates |
| `n_steps` | `512` | New experiences collected before updating |
| `batch_size` | `256` | Experiences per optimization minibatch |
| `n_epochs` | `5` | Passes over each collected rollout |
| `gamma` | `0.95` | Discount applied to future rewards |
| `gae_lambda` | `0.9` | Controls the advantage estimator’s bias/variance tradeoff |
| `clip_range` | `0.3` | PPO probability-ratio clipping parameter |
| `ent_coef` | `0.00238306` | Encourages exploration |
| `vf_coef` | `0.431892` | Weight of the critic’s prediction loss |
| `max_grad_norm` | `2` | Limits gradient magnitude |
| `log_std_init` | `−2` | Initial action standard deviation is approximately `0.135` |
| `ortho_init` | `False` | Disables orthogonal network initialization |

We used **one environment**, running on CPU with one PyTorch thread.

These settings came from the RL Baselines3 Zoo Humanoid baseline. They were **not tuned specifically for our contact-based falling rule**, which differs from the standard task.

One parameter worth examining is `gamma=0.95`. A reward 20 steps ahead receives a discount factor of:

\[
0.95^{20}\approx0.36
\]

Twenty steps represent only about **0.3 simulated seconds**. This gives relatively strong emphasis to near-term reward. It is a possible tuning concern, not proof of why training failed.

**8. Normalization**

`VecNormalize` maintains running statistics to scale observations and rewards during training. This helps inputs with very different magnitudes—angles, velocities, and forces—work together.

Evaluation uses frozen observation statistics and reports **raw environment rewards**. The normalization file must match the policy checkpoint; loading the policy without its corresponding statistics changes what the network effectively sees. [Normalization documentation](https://stable-baselines3.readthedocs.io/en/master/guide/vec_envs.html#vecnormalize)

**9. How we selected the best policy**

During the long run, we evaluated every **100,000 training steps**, using five fixed evaluation seeds and deterministic actions.

We recorded:

- Total reward.
- Episode length.
- Forward distance.
- Fraction reaching 1,000 steps without falling.

**“Best” means highest average evaluation reward**, not longest survival or most natural gait. Because these same five seeds were repeatedly used for checkpoint selection, a stronger final assessment would also use fresh seeds.

The selected checkpoint, from about **8.8 million steps**, averaged:

| Metric | Result |
|---|---:|
| Episode reward | 1,214.6 |
| Episode length | 170 steps |
| Forward distance | 6.47 meters |
| Full-length episodes | 0 of 5 |

That is only about **2.55 seconds before falling**. It demonstrates why higher reward alone was insufficient evidence of successful walking. The next investigation should examine the motion and reward components, then test changes to the objective or training method rather than assume that more steps will fix it.

**1. Diagnose how it falls**

That distinguishes different problems:

| Observed behavior | Possible issue |
|---|---|
| Lunges forward and falls | Forward-speed reward may favor short bursts |

| Moves violently or jitters | Exploration or rapidly changing motor commands |

**2. Reward a controlled walking speed**

Currently, faster forward movement keeps increasing reward. We could instead reward matching a target speed, initially around **0.5 m/s**:

\[
r_{\text{speed}}=\exp\left(-\frac{(v_x-v_{\text{target}})^2}{\sigma^2}\right)
\]

This rewards being near the requested speed rather than accelerating indefinitely.

Other candidates are:

- **Torso orientation:** reward keeping its upward axis aligned with vertical. Our current “upright” reward only checks height.
- **Sideways motion:** a modest penalty for lateral velocity.
- **Action smoothness:** a small penalty on \(\|a_t-a_{t-1}\|^2\). We should then include the previous action in the observation.
- **Explicit fall penalty:** worth testing, although excessively large penalties can discourage movement.

I would introduce these separately so we can identify what actually helps.

**3. Test a longer planning horizon**

Our current discount factor is **`gamma=0.95`**, with an action every 0.015 seconds. Future rewards lose weight quickly.

A useful comparison is:

| Experiment | `gamma` | Approximate discounted horizon \(1/(1-\gamma)\) |
|---|---:|---:|
| Current baseline | 0.95 | 20 steps ≈ 0.3 seconds |
| Longer horizon | 0.99 | 100 steps ≈ 1.5 seconds |
| Longer still | 0.995 | 200 steps ≈ 3 seconds |

These horizons are rough interpretations, not hard limits. A larger gamma might make future falls matter more, but can also make learning harder. I’d test **0.99 first**, keeping the reward unchanged.

**4. Use curriculum learning**

This is especially relevant to your project. One proposed curriculum is:

| Stage | Task | Example advancement criterion |
|---|---|---|
| 1 | Stand and balance | Survive 500 steps in most evaluation episodes |
| 2 | Walk slowly at 0.25 m/s | Stay upright while tracking the requested speed |
| 3 | Walk at 0.5 m/s | Maintain speed over longer episodes |
| 4 | Walk at 1 m/s | Complete 1,000-step episodes reliably |

The thresholds would be experiment settings, not established optimal values.

**5. Improve the experiment design**

- Use several training seeds—ideally at least three.
- Keep the total interaction budget comparable.
- Measure survival, speed error, and forward distance.
- Evaluate on fresh seeds beyond those used to select checkpoints.
- Inspect videos as well as reward.

That changes the project’s assumptions because demonstrations are now available. DeepMimic demonstrates this approach for physics-based character control. Prompt:

What is the current reward equation?

Response:

With the current `Training_run/config.py`, the **reward per action** is:

\[
\boxed{
r =
1.25v_x
+ 5e^{-((h-1.4)/0.15)^2}\,\mathbf{1}_{\text{not fallen}}
+ H
- 0.2\sum_{i=1}^{17}u_i^2
- \min\left(5\times10^{-7}\sum_j F_j^2,\;10\right)
- 200\,\mathbf{1}_{\text{fall}}
+ 500\,\mathbf{1}_{\text{finish}}
}
\]

The heading term is:

\[
H =
0.5c_{\text{torso}}
+0.5c_{\text{pelvis}}
+0.25c_{\text{left foot}}
+0.25c_{\text{right foot}}
\]

| Symbol | Meaning |
|---|---|
| \(v_x\) | Whole-body center-of-mass forward velocity, in m/s |
| \(h\) | Root height in meters—not head height |
| \(u_i\) | Motor command, bounded between −0.4 and +0.4 |
| \(F_j\) | Components of the external body forces and torques |
| \(c_{\text{body}}\) | Horizontal forward alignment: +1 forward, 0 sideways, −1 backward |
| \(\mathbf{1}\) | Equals 1 when the condition occurs, otherwise 0 |

In practical terms:

- **Forward motion:** +1.25 per m/s.
- **Standing height:** up to +5, peaking at 1.4 meters. This term checks height, not torso tilt.
- **Facing forward:** up to +1.5 when all four measured bodies face forward.
- **Effort and contact:** subtract penalties.
- **Fall:** −200 and terminate.
- **Finish:** +500 and terminate after advancing 20 meters. A simultaneous fall takes precedence.

These active rewards are **not multiplied by the action duration**. Timeout has no separate terminal bonus or penalty.

**Currently disabled:** knee coordination, sideways-motion penalties, target-speed tracking, additional distance reward, and action smoothing—their weights are zero.

This describes the current defaults. Previously saved runs use their own settings and reward snapshots.

| **Foot clearance and less slipping** | Lift and advance each foot instead of sliding | Can produce exaggerated lifting or hopping |
| **Reference-motion imitation** | Follow an example running gait | Requires a suitable reference motion |


More negative means more knee bend. The reward is reduced when either knee misses its target, and it is gated by forward motion and upright posture.

| Knee weight | Maximum knee reward per action |
|---:|---:|
| 2 | 0.03 |

| 30 | 0.45 |

Those maxima assume perfect tracking and fully satisfied movement/posture gates. Actual rewards can be much smaller.

A reasonable first comparison is **weights 0, 10, and 30**, keeping the knee angles, frequency, and other settings fixed. These are experimental values, not established optimal settings.

**2. Reward knee bending during actual swing**

This is my preferred next implementation if the fixed rhythm fails.

Instead of a clock dictating the motion:

- When a foot leaves the ground and advances, encourage its knee to bend.
- When that leg supports the body, allow it to extend.
- Encourage alternating support between legs.

This connects knee movement to stepping. We would need to avoid rewarding foot lifting alone, because the agent could learn to hop.

**3. Address sliding directly**

Your observation that it “wiggles forward” may indicate foot sliding rather than just insufficient knee bending.

We could add:

- A modest penalty for horizontal foot velocity **while the foot contacts the ground**.
- A bounded reward for appropriate foot clearance during swing.
- A reward for alternating forward foot placements.

These target the unwanted behavior more directly, but require code changes and careful testing.

**4. Use a reference gait**

For stronger control over motion style, reward matching a walking/running reference. Methods such as DeepMimic combine motion imitation with task rewards, but this introduces demonstration data into the project. [DeepMimic paper](https://arxiv.org/abs/1804.02717)

**I’d start with the existing knee-weight experiment.** Inspect both knees in the video and compare distance and falls—not just reward. If it bends more but still slides, the next experiment should target foot contact and slipping.
